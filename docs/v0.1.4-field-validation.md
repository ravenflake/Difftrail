# Difftrail v0.1.4 field-validation checklist

This checklist is the gate between the synthetic validation already in CI and
the first real Windows field validation. It is deliberately written for a
normal desktop, not a lab environment. The goal is to learn whether Difftrail
collects reliably, preserves privacy, and produces useful evidence without
pretending that a timestamp correlation proves causality.

Do not release v0.1.4 solely because the automated suite is green. Record the
results below on at least one real Windows installation first.

## Current readiness

| Area | Current evidence | Status |
| --- | --- | --- |
| Deterministic ranking | `python -m difftrail validate` | Automated |
| Scanner-backed fixture replay | `python -m difftrail validate-scenarios` | Automated |
| Event Log normalization | Unit coverage for reset, restart, shutdown, hang, and crash events | Automated |
| Clean install and uninstall | CI installer smoke test | Needs local confirmation |
| Upgrade from v0.1.3 | Not exercised on a real host | Pending |
| Background watcher over time | No multi-day host data yet | Pending |
| Real incident usefulness | Synthetic only | Pending |
| Installed-runtime behavior | Not exercised outside CI | Pending |

The CI installer smoke test verifies a silent install and uninstall in an
isolated temporary directory. It is not evidence of an interactive launch,
journal migration, background watcher, or normal-user-profile behavior.

## 1. Capture the test context

Record this information before changing anything:

- Date and local time.
- Windows edition, version, and build.
- Difftrail version and installer filename.
- Whether this is a clean install, an upgrade, or an existing checkout.
- Whether the machine is being used normally during the test.
- The database path being tested.

Use a disposable database for deliberate fixture or CLI tests. Do not mix
fixture data into the journal you intend to use for real incidents.

## 2. Clean install, upgrade, and uninstall

Run two independent paths, using a clean machine or clean user profile for
each path. Keep the existing journal backed up before the upgrade or uninstall
path:

### Fresh v0.1.4 install

1. Install the candidate v0.1.4 Windows installer directly.
2. Launch Difftrail and confirm that the Overview and System health views load.
3. Run the initial scan and confirm that the first snapshot is quiet.
4. Open System health and run `doctor --json` against the active database.

### v0.1.3 upgrade

1. Install the current v0.1.3 Windows installer as the current user.
2. Launch Difftrail and confirm that the Overview and System health views load.
3. Run the initial scan and confirm that the first snapshot is quiet.
4. Open System health and run `doctor --json` against the active database.
5. Upgrade from v0.1.3 to the candidate v0.1.4 installer.
6. Confirm that the existing journal opens, migrations are up to date, and
   previous events and investigations remain visible.
7. Uninstall the application and confirm the journal is not silently deleted.
8. Reinstall and confirm that the preserved journal can still be opened.

Pass criteria:

- The installer completes without an unexpected elevation or launch failure.
- The app opens after both clean install and upgrade.
- `doctor --json` reports an up-to-date schema and a healthy SQLite journal.
- No scan remains stuck as `running` after the scan has finished or failed.
- Uninstall removes the application but does not erase the user journal.

## 3. Baseline and watcher reliability

After installation, take a quiet baseline before interpreting any later
change. Enable Background watcher from Automation, or review and run the
installer script from the repository:

```powershell
python -m difftrail --db "$env:LOCALAPPDATA\Difftrail\difftrail.db" scan
python -m difftrail --db "$env:LOCALAPPDATA\Difftrail\difftrail.db" doctor --json
```

Leave the computer in normal use for at least 48 hours; a seven-day run is
preferable. Include at least one normal reboot and one sleep/wake cycle. Do
not deliberately crash Windows or uninstall a driver just to create a test
case.

At the start and end of the run, record a report window that matches the
observation period. For the minimum 48-hour run, use `--days 2`; for a
seven-day run, replace it with `--days 7`:

```powershell
python -m difftrail --db "$env:LOCALAPPDATA\Difftrail\difftrail.db" validate-host --days 2 --json
python -m difftrail --db "$env:LOCALAPPDATA\Difftrail\difftrail.db" doctor --json
```

Pass criteria:

- The watcher continues to run after reboot and resumes after sleep/wake.
- Completed scans are `ok` or honestly `partial`; a provider failure does not
  masquerade as a clean scan.
- No unexplained repeated changes are produced by service runtime state,
  localized display text, or ordinary watcher activity.
- No abandoned scan remains indefinitely as `running`.
- The journal remains readable and the database size does not grow without a
  clear explanation.
- Notifications and investigation drafts are not duplicated on every scan.

Record a numeric overhead sample when the optional validation dependency is
available:

```powershell
python -m pip install psutil
python -m difftrail --db "$env:LOCALAPPDATA\Difftrail\difftrail.db" overhead --record --json
```

Treat overhead as machine-specific evidence. Do not turn one host's CPU or
memory result into a universal product guarantee.

## 4. Real incident observations

Capture incidents that happen naturally. Useful cases include:

| Incident | Evidence to look for |
| --- | --- |
| Application update followed by a crash or hang | App version transition, Event Log symptom, safe application name |
| Display-driver reset or graphics failure | Driver/package change, event 4101, graphics ranking |
| Audio or peripheral replacement | Device add/remove transition, matching symptom |
| New service, task, or startup entry | Persistence transition, startup symptom, source-level evidence |
| Unexpected restart or shutdown | Event 41 or 6008 and any changes recorded before it |
| Windows update near a symptom | HotFix transition, update history target, confidence limits |

For each incident, save a small record outside the database:

- What the user noticed and when.
- The selected onset used in Difftrail.
- The top candidate and rank.
- Assessment state: `candidate_found`, `insufficient_evidence`,
  `no_recent_changes`, or `limited_coverage`.
- Whether the candidate was actually useful.
- Any important counter-evidence or provider warning.
- Whether the suggested diagnostic target was safe and relevant.

Do not mark a result `correct` merely because it sounds plausible. Use the
feedback command only when the real incident gives you a reason to believe the
candidate was useful:

```powershell
python -m difftrail --db "$env:LOCALAPPDATA\Difftrail\difftrail.db" feedback <incident-id> --outcome correct --event-id <event-id>
```

## 5. Privacy and portable reports

Export a redacted bundle from a real journal and validate it before sharing:

```powershell
python -m difftrail --db "$env:LOCALAPPDATA\Difftrail\difftrail.db" export-bundle --output .\diagnostic.difftrail.json --days 30
python -m difftrail validate-bundle .\diagnostic.difftrail.json --json
```

Pass criteria:

- Bundle validation succeeds.
- The bundle contains no SQLite database, raw Event Log message, process ID,
  username, absolute path, or watcher command line.
- The bundle remains useful enough for a support conversation: time windows,
  source names, safe change summaries, assessment, evidence signals, and next
  actions are still present.
- Exporting again to the same path does not overwrite the live database.

Delete test bundles after inspection if they contain real machine metadata.

## 6. Promotion gate for v0.1.4

The release candidate should not be promoted until all of these are true:

- CI is green, including the Windows installer smoke test.
- Clean install, upgrade, launch, and uninstall have passed on a real Windows
  machine.
- At least 48 hours of watcher use completed without data loss or unexplained
  stuck scans; seven days is the preferred target.
- At least three naturally occurring or safely observed incidents have been
  reviewed, including one case with incomplete evidence or a provider warning.
- At least one redacted bundle has been validated and manually inspected.
- Any false positives, missed changes, installer problems, or confusing UI
  states are filed before deciding between v0.1.4 and a larger v0.2.0 scope.

These gates measure readiness and usefulness. They are not a claim that
Difftrail can establish causality for every Windows problem.
